Tech note 02 / System map

An LLM is a model inside a larger system.

The neural network supplies capability. Data, adaptation, tools, evaluation, and boundaries determine what users actually experience.

01

Capability

Pretraining builds a general pattern engine.

A base language model learns by predicting the next token across a large text corpus. The objective is simple, but the pressure is broad: the network must compress regularities in language, facts, formats, code, and many styles of reasoning into its parameters.

Scale links model size, data, and computation. Increasing only one eventually wastes the others. Good training therefore begins as a resource-allocation problem: choose the data mixture, model capacity, batch schedule, and compute budget as one design rather than independent knobs.

02

Behavior

Adaptation turns completion into assistance.

The base objective teaches continuation, not cooperation. Adaptation data demonstrates instruction following, conversation structure, refusal boundaries, and preferred answer shapes. Feedback then distinguishes responses that are merely plausible from those that are useful, honest, and safe.

This stage can alter behavior dramatically without rebuilding all underlying knowledge. It also creates a critical distinction: capability and behavior are related but not identical. A system may know how to do something while policy or context determines whether and how that capability is expressed.

03

Action

Tools convert language into consequences.

A standalone model emits tokens. A tool-enabled system can search an allowed corpus, run code, inspect files, call services, or change an application. The surrounding runtime must define schemas, permissions, timeouts, observations, and the evidence required before an action is accepted.

The attack surface grows at the same moment. Untrusted content can contain adversarial instructions; tools may carry privileges the model should not inherit; generated commands can be syntactically valid and operationally wrong. Strong systems separate data from instructions and make authority explicit at every boundary.

04

Operation

Evaluate the complete loop, not only the answer.

Measure the prompt, environment, actions, observations, outcome, latency, cost, and safety events together. A polished final response can hide an invalid tool call or an irreversible side effect. A correct result can still be too slow or expensive for the product.

The operational model is therefore layered: a checkpoint at the center, a context builder around it, a controlled action surface, independent checks, and observability across the run. That is the object users trust—and the object engineers must improve.
