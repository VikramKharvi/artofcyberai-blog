01

Fidelity

Architecture is a specification, not a visual resemblance.

Match vocabulary size, context length, embedding width, layer count, head count, activation, normalization placement, biases, and parameter sharing. Small differences can change parameter count, optimization, and compatibility with reference weights.

Initialization also carries architectural intent. Residual branches may need scale adjustments as depth grows. Tied token and output weights remove duplicated parameters. Loading a known checkpoint and comparing shapes provides a fast structural test before expensive training begins.

02

Data

The loader determines what the optimizer actually sees.

Large corpora are tokenized into shards that must be streamed, partitioned, and resumed deterministically. A batch is defined not just by sequences per device, but by the total number of tokens contributing to one optimizer update.

Gradient accumulation reconciles the desired token batch with limited memory. In distributed training, each worker must receive distinct data while maintaining a shared notion of step, epoch, and checkpoint. If data order or token counts drift, two nominally identical configurations are no longer comparable.

03

Throughput

Hardware-aware math changes the feasible experiment.

Mixed numerical formats reduce memory traffic and make specialized matrix units available, while selected reductions remain in higher precision for stability. Fused attention avoids materializing large intermediate matrices. Compilation can combine operations and remove launch overhead.

These optimizations should preserve the reference loss within an understood tolerance. Measure tokens per second, accelerator utilization, memory, and time per step after warm-up. Optimization without measurement is only a code change; measurement turns it into a systems result.

04

Evidence

A run needs more than a falling training loss.

Track held-out loss, fixed downstream checks, sample quality, throughput, and checkpoint health. Save the exact configuration, code revision, tokenizer, data manifest, random seeds, optimizer state, and runtime versions. A benchmark should be measured on a stable procedure, not selected after seeing the result.

Performance is part of intelligence.

Faster, stable training allows more iterations, cleaner comparisons, and better use of a fixed budget. Runtime efficiency also determines how much useful work the deployed system can complete. Performance is part of the experiment—not decoration around it.
