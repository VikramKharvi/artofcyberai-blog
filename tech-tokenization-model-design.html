Tech note 01 / Tokenizers

Tokenization is a model design decision.

Before a model sees language, a tokenizer decides which distinctions are cheap, expensive, visible, or fragmented.

01

Representation

Text has several identities before it becomes an ID.

A string can be viewed as characters, Unicode code points, encoded bytes, or learned token pieces. Those layers are related, but they are not interchangeable. Unicode gives characters stable identities; UTF-8 turns those identities into bytes; the tokenizer groups byte sequences into a vocabulary that a model can index.

Starting from bytes gives complete coverage: any valid input can be represented. The cost is length. One byte per unit creates long sequences, while one token per word creates an impossible vocabulary and handles unfamiliar words poorly. Tokenization is the compromise between those extremes.

02

Compression

Merge rules trade vocabulary size for sequence length.

A byte-pair tokenizer begins with small units, counts adjacent pairs, and repeatedly merges useful pairs. Common patterns become single tokens; rare patterns remain compositions of smaller units. The result is a learned compression scheme whose merge order matters.

Training the tokenizer and encoding text are separate operations. Training produces a fixed vocabulary and ordered merge table. Encoding must apply that table deterministically, while decoding must reconstruct the original bytes. If either side improvises, the model no longer sees the same language it was trained on.

A tokenizer is a compression algorithm with a permanent API.
03

Behavior

The vocabulary changes what is easy for the model.

Token boundaries affect arithmetic, spelling, code, multilingual text, and names. A frequent English fragment may occupy one position while a less represented script expands into many. Numbers may split differently depending on spacing. Code punctuation can become either compact structure or a long chain of fragments.

These choices change effective context length and the number of prediction steps needed to express an answer. They also explain why adding vocabulary later is not a cosmetic edit: the embedding table, output layer, saved weights, and every downstream data artifact depend on the token IDs.

04

The contract

Treat the tokenizer like versioned model code.

Record its normalization rules, byte encoding, vocabulary, merge order, pattern rules, and special-token policy. Test round trips across languages, whitespace, emoji, malformed bytes, code, and long repeated strings. Measure both compression and boundary quality on the domains that matter.

A model checkpoint without its exact tokenizer is incomplete. The two artifacts form one interface: text enters on one side, integer IDs cross the boundary, and text must return intact on the other.
